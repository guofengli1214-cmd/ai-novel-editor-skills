# 文件、版本与交接协议

本协议版本为 1。脚本是文件可靠性辅助工具，不能证明小说好、子 agent 身份真实或作者确实同意。主 agent 仍须对照宿主派工结果与用户原话验收；文件管理脚本的写命令由资料子 agent 执行，正文创作与修改仍由创作子 agent 承担。

## 1. 目录与命名

```text
书名/
  索引.md
  第0001章-有意义的标题.md        当前采用正文，全书连续章号
  创作约定/                    意图、作者决定、语言标准、状态、交接与任务计划
  大纲/                        全书、阶段、章节与场景计划
  人物/                        基础人物档案
  世界与地点/                  地点、规则、组织、世界历史
  连贯性记录/                  故事时间、角色状态与知情等
  摘要/                        章、阶段、全书摘要
  审稿与修订/                  评审JSON及可读意见、修订和变化记录
  草稿与备选/                  未采用正文、候选资料、独立备选方案
  历史版本/                    快照及操作备份
```

每个活动目录都有 `索引.md`。工具生成的历史快照与 `历史版本/chapter-<operation_id>/` 采用日志只读保留，由 `历史版本/索引.md` 链接 manifest 或 journal，不向它们内部补写索引。根据实际内容增加 `故事线/`、`关系与成长/`、`事件/`、`线索与悬念/`、`资源/`、`曲线与节奏/`，不预建所有空表。文件名如 `人物-林舟-调查记者.md`；稳定对象标识写在文件里，用于改名和别名追踪。

顶层只保留当前正式章节和必要索引，不能将草稿、导出合集或旧稿放进顶层。分卷在目录和计划中表示，章号不重置。标题变更时更新状态、引用、所有受影响索引；保留旧名作检索别名。

重要文本优先 Markdown；机械状态和评审可用 UTF-8 JSON。状态文件是普通文件，不能引入 SQLite、FTS、向量库或外部服务作为记忆依赖。

## 2. 索引与检索

`novelctl index` 管理 `<!-- novelctl:auto:start -->` 与 `<!-- novelctl:auto:end -->` 之间的文件链接块；块外是资料子 agent 维护的用途、内容介绍、状态、查询入口和阅读顺序。自动块只列文件，不等于完整语义索引。

顶层索引须有按章号排序的正式目录、每章一句介绍、当前进度和写前必读入口。分类索引说明每个子文件/子目录的内容及正式、草稿、历史、待核实状态。重建自动链接不能抹掉手写说明。归档快照内容不可为修索引而随意改动。

先索引定位，再按文件名、对象别名和关键词搜索，最后读原文；有 `rg` 用 `rg`，没有时用宿主文本搜索或标准库。搜索不到不等于从未写过。摘要帮助定位，事实引用须有章节、片段及核对哈希；找不到旧片段就标过期并重查。

## 3. 工具入口

命令中的 `SKILL` 是当前 Skill 文件夹的绝对路径；`BOOK` 是作品绝对路径。由执行者用真实路径替换，不复制为字面参数。Python 3.9+，无第三方运行依赖。示例使用 `python`，先确认 `python --version`；Linux/macOS 可替换为 `python3`，Windows 可替换为 `py -3`。下列 `$SKILL` / `$BOOK` 按 Bash 展示；PowerShell 可直接填带引号的实际路径，不能照抄 Bash 变量赋值。`init` 自动创建缺失的作品库；书名须是跨平台单个目录名，拒绝 Windows 非法字符、设备保留名和尾随空格或点，初始化失败清理本次半成品。作品内部的符号链接和 Windows reparse point/junction 不受支持，作品根目录可通过 junction 访问。

```bash
python "$SKILL/scripts/novelctl.py" init --parent /绝对/作品库 --title 雾港来信
python "$SKILL/scripts/novelctl.py" index --book "$BOOK"
python "$SKILL/scripts/novelctl.py" check --book "$BOOK"
python "$SKILL/scripts/chapterctl.py" check --book "$BOOK"
python "$SKILL/scripts/taskctl.py" check --book "$BOOK"
python "$SKILL/scripts/bookctl.py" manifest --book "$BOOK"
python "$SKILL/scripts/bookctl.py" check --book "$BOOK"
python "$SKILL/scripts/novelctl.py" snapshot --book "$BOOK" --label 第十二章采用前
python "$SKILL/scripts/novelctl.py" restore --book "$BOOK" --snapshot /绝对/快照目录
python "$SKILL/scripts/novelctl.py" export --book "$BOOK" --output /绝对/导出/雾港来信.md
python "$SKILL/scripts/chapterctl.py" --help
```

主 agent 只运行 `check`、`bookctl manifest` 等只读命令；文件管理脚本的写命令交资料子 agent 执行，不能因属机械操作就由主 agent 代写。`check` 成功仅代表其已实现的文件检查通过，不代表文学、全部语义索引或资料事实均正确。

日常 `novelctl check`、`chapterctl check` 与 `bookctl manifest` 可显式加 `--skip-snapshots`，跳过历史快照 payload 的全量验证；此时不能据通过宣称归档完好。默认完整检查，`restore`、`chapterctl finish`、`bookctl check` 不使用该快速模式。

任务管理的单文件、状态、阶段模板、依赖及命令见[阶段任务与验收](task-management.md)。`taskctl check` 检查当前任务记录，允许存在正常未执行项；关键动作另用 `gate` 核验对应前置任务。任务文件是 `创作约定/任务计划与验收.md`，不再创建一份竞争的 JSON 任务库。

## 4. 正式状态与章节门槛

`创作约定/作品状态.json`：

```json
{
  "schema_version": 1,
  "title": "雾港来信",
  "chapters": [],
  "pending_operations": []
}
```

正式章节条目由工具登记，至少含 `number`、顶层相对 `path`、正文 `sha256`、`writer_task`、`review_path`、`reviewer_task`。扩展字段保留。不能手工改哈希来隐藏用户修改，应先调查，再进入重新评审和同步流程。

新建作品状态额外包含 `task_management: true`，并初始化任务文件。旧状态没有此字段仍可读取；旧书迁入后以任务文件存在启用门槛。标记已启用却缺文件属于恢复问题，不能通过删文件绕过。采用请求可带 `task_stage`；采用前核验当前草稿与评审对应的阶段任务，采用结果关联阶段及操作标识。资料子 agent 在采用成功后登记 `adopt` 任务的正式章节证据和操作号，再运行 `finish`，成功后才验收 `sync`。不得要求 `finish` 前先验收 `sync`。

章节采用由 `chapterctl.py adopt --book BOOK --request REQUEST.json` 验证。采用后待完成操作仍在，资料子 agent 更新记忆、历史和交接，运行 `index`，再用 `finish --book BOOK --request REQUEST.json` 关闭。`adopt` 请求与 `finish` 请求是不同的 JSON 文件；后者携带采用命令返回的 `operation_id`。请求支持文件路径、`@文件路径` 或直接 JSON；优先使用文件，避免 shell 转义问题。具体字段与示例见脚本 `--help`，不得猜测字段。

变化记录的 `categories` 使用脚本约定的英文键，值为 `updated` 或 `unchanged`；`pending` 不能关闭操作。每次采用后 `summaries`、`history`、`indexes`、`handoff` 四项必须为 `updated`，其余类别按实际变化判断。`checked_sources` 列实际核对文件，`updated_files` 列已更新文件及其哈希，`category_files` 将每个 `updated` 类别关联到这些文件，`handoff` 指明接续文件和章号；接续正文至少出现 `第1章`、零填充的 `第0001章` 或完整正式章文件名中的一种，章号须对应本次采用。这是机械证据入口，资料内容是否充分仍由主 agent 抽查、必要时派子 agent 复核。索引刷新后再计算受影响文件哈希；不要把不断变化的状态文件或变化记录自身列入自身哈希清单。

共同门槛：当前稿哈希与评审一致，实际写作者与评审者不同，文学与连贯性覆盖齐全，无未解决硬冲突，作者授权对应版本，新建不覆盖已有文件，替换时旧哈希匹配。评审问题的 `severity` 为 `hard`、`soft` 或 `info`，`status` 为 `open`、`resolved` 或 `waived`，硬冲突只能 `resolved` 后采用。全部采用记录可追溯。文件中的 ID 只是申报，主 agent 必须对照真实宿主记录，不能凭不同字符串认定存在独立 agent。

采用后“待同步”不等于完成。变化记录要覆盖意图、人物、成长、关系、世界、故事线、事件、线索、知情、资源、曲线、节奏、摘要、历史、索引、交接；状态可为已更新、检查无变化、待处理。未完成项须保留，不能删除 pending 来伪造完成。

### 全书定稿与章节采用的区别

`chapterctl finish` 仅表示该次章节采用的资料同步完成。全书定稿还需要对当前完整稿的整体阅读、必要结构修订及复核；阶段评审不能充当完整全稿评审。人类可读报告按[作品资料约定](story-records.md)记录阅读范围、突出成就、最大不足、重大问题处理或保留理由、结构修订及复核、授权和外部反馈限制。没有必要结构改动时写明依据，不强制为流程改稿。没有外部读者可按真实授权内部定稿，报告注明仅经 AI 阅读。

资料子 agent 根据实际评审结果写入 `审稿与修订/全书定稿记录.json`，不把自己的资料整理任务冒充整体评审。该记录采用独立的 `schema_version: 1`，不改变已有作品状态格式，也不要求未完稿作品补建。字段如下，示例中的路径、身份和哈希须替换为真实产物：

```json
{
  "schema_version": 1,
  "chapters": [
    {"number": 1, "path": "第0001章-夜班.md", "sha256": "实际正文SHA-256"}
  ],
  "reviewer": {"task_id": "实际整体评审任务", "agent_id": "实际评审者"},
  "reading_scope": "full",
  "verdict": "ready",
  "reading_report": {"path": "审稿与修订/全书整体阅读.md", "sha256": "实际报告SHA-256"},
  "revision_report": {"path": "审稿与修订/结构修订与复核.md", "sha256": "实际报告SHA-256"}
}
```

`chapters` 使用 `bookctl.py manifest --book BOOK` 返回的真实完整清单，按章号阅读顺序保留 `number`、`path`、`sha256`，不能手填部分章节或只放摘要。`reviewer` 是未参与当前全稿撰写的真实评审子 agent，主 agent 对照宿主任务核验；文件内不同字符串不证明独立身份。`reading_scope: full` 和 `verdict: ready` 是实际阅读范围与文学结论的申报，不是脚本认证。两个报告均为作品内 `审稿与修订/` 下的非空 Markdown，分别绑定实际内容哈希；可以引用同一份包含全部阅读、修订与复核内容的综合报告。

启用任务管理的作品还须通过定稿阶段 `finalize` 的前置任务检查，`whole_recheck` 的输入覆盖当前全部正式正文路径与哈希；通过 `bookctl check` 并核验内容后才验收 `finalize`。有多个相关阶段时在定稿记录中用 `task_stage` 指定，不能用其他章节阶段或旧任务勾选代替当前全稿复核。

主 agent 在作者参与约定满足、重大问题已处理或有明确保留理由后，运行 `bookctl.py check --book BOOK`，自定义记录使用 `--record 审稿与修订/相对文件名.json`。它只读检查现有章节门槛、非空完整清单、评审申报身份与写作者不同、报告文件及哈希、检查期间文件未变化。内容、章号/阅读顺序、路径、章节数量或所引报告变化时，旧记录检查失败；资料子 agent 保留历史依据，派评审复核受影响范围与整体效果，再据真实新结论更新记录，不能只换哈希掩盖过期评审。语义质量、是否实际读完、授权与独立性仍由主 agent 验证，不计算文学分数。

已经通读旧完整版本后发生局部修订，可用“旧全稿通读 + 变化及关联范围补读”形成当前稿的完整覆盖证据：报告列旧/新章节清单、改动映射、实际补读范围和沿用未改部分结论的理由。影响广泛、顺序显著改变或无法界定关联范围时扩大到重新通读；没有旧全稿通读证据时，不能只读改动就申报 `full`。

缺少或过期的全书定稿记录不阻止普通续写、逐章同步和工作稿导出。声明“全书定稿”时必须通过上述整体证据与版本检查；普通 `novelctl check`、`chapterctl check` 或 `finish` 通过均不能替代它。

## 5. 历史与故障恢复

重要采用、大改或回退前 `snapshot`，其清单记录文件哈希。快照含正文、资料、状态，不递归复制历史；还原前校验快照并保留当前整书恢复副本。恢复完整作品，不只恢复正文。恢复后重新检查引用、资料、旧评审对应版本和下一章是否仍成立。

流程中断时先读 `pending_operations` 及对应操作记录：确定正式正文是否已更新、哪个版本评审有效、哪些资料尚未完成。不要重新采用同一章或重复记事件、扣资源。可以从有效稿继续同步；输入已变化或无法安全续办时，资料子 agent 按已验证的采用前快照恢复整个现场，保留异常证据再重新派工。

进程被强杀后锁目录可能残留。先停止该作品的全部写入任务，核对状态的 `pending_operations`、锁的 `owner.json` 和 `历史版本/chapter-<operation_id>/journal.json`，确认没有活写入者；资料子 agent 才可执行显式解锁：

```bash
python "$SKILL/scripts/chapterctl.py" unlock --book "$BOOK" --request /绝对路径/解锁请求.json
```

请求为 `{"confirm_no_writer":true,"expected_pending":[]}`；有 pending 时 `expected_pending` 必须列出全部当前 `operation_id`，例如 `["实际操作号"]`。Windows 新锁记录持锁进程的创建时间，解锁时同时比较 PID 与创建时间；同 PID 已被另一进程复用时，不将其误认成原写入者。同一持锁进程仍存活时拒绝解锁；旧锁缺少创建时间时仍保守拒绝活 PID，读取进程信息失败也不能作为绕过依据。待办不匹配或锁内未知文件同样拒绝；缺少 owner 的空残留锁也须操作者显式确认。解锁不删除 pending、备份或日志，不代表采用或同步完成，之后仍沿原操作恢复。不要删除锁内不明文件来强行通过。

不得在写入任务运行时恢复。主 agent 调度保证一个作品同一时刻只有一个采用/恢复写入者；各并行任务写隔离候选目录。工具使用原子文件替换和待办记录，不能把普通文件更新宣称成数据库事务；多进程异常仍需检查和恢复。

单章回退与整书恢复不同：资料子 agent 从已验证快照中提取目标旧章到候选区，保留当前其他章节；重新派评审核对它与当前后文及资料的冲突，必要时交创作子 agent 修订。通过后用当前正式章哈希作为 `expected_sha256` 重新采用，并重建受影响资料。不能为恢复一章而悄悄回退其他章，也不能直接把旧章复制到顶层绕过评审。

用户手工改动：先保存，读取差异，派评审核查影响，再经正式更新同步资料。快照清单损坏或路径越界时不恢复、不覆盖，不靠跳过校验“修好”。恢复产生的额外副本由用户决定清理，不默认删除。

手改正文导致清单哈希不符时，不能直接再次 `adopt`，也不能改清单哈希消警：资料子 agent 先将手改完整保存到候选区并核对副本哈希，再从上次采用备份或已验证快照找到与清单旧哈希一致的正文。对候选稿完成独立评审后，在确认顶层仍是已保存的那份手改、没有新并发修改的条件下，资料子 agent 将旧采用正文机械复位，随即用它的旧哈希作为 `expected_sha256` 采用已评的新稿。全过程保留手改副本和操作记录；找不到可信旧正文时暂停并报告恢复缺口，不自行编造旧版本。

## 6. 作者决定与备选方案

记录真实消息摘录、来源日期或平台可用引用、选择对象及稿件哈希。无外部消息编号时保存可核实的原话及上下文，不伪造编号。逐章或试写批准须对应当前版本；既有授权没有改变就沿用，不重复索要普通操作批准。

备选方案在 `草稿与备选/方案-名称/` 保存独立目录及索引、分叉哈希、差异与局部资料。不能写入当前正式状态。当前工具只管理一套采用章节，分支比较由子 agent 读各方案差异；切换方案不是移动一个指针，需执行影响核对、逐章评审和资料整合。不得声称支持尚未实现的自动多分支事务。

### 章节与场景管理

新章走草稿—评审—采用；章内场景可独立试写和修订，采用时整合为被评审的完整章，不把互不兼容的场景版本直接拼成正式章。

改标题、重排章节或插章前，资料子 agent 列出路径、章号、引用、阅读顺序、信息揭示和时间线的影响，保存快照及待完成记录。纯文件改名由资料子 agent 机械迁移并更新状态；改正文由创作子 agent 执行。重排可能改变读者知情和场景承接，即使文字哈希没变，也要由评审子 agent 按新阅读上下文复核受影响章，保留新旧顺序及评审依据。

删除正式章须依据作者要求或既有授权执行，先保留快照和原因，将该章退出当前采用清单，保留可恢复旧稿，不直接永久销毁。沿故事线、事件、知情、资源和引用追查依赖，补足后续因果或标记待修。草稿放弃也保留有意义的备选与决定记录。

当前辅助脚本没有自动重排、改名或软删除命令；这些操作由资料子 agent 按上述规则维护普通文件及 JSON，并用两个 `check` 验证。不能使用手工维护来规避正文变化的独立评审与资料同步门槛。

## 7. 导入与导出

TXT/Markdown 导入由资料子 agent 保存原稿到有索引的来源目录、记录来源与哈希，按阅读顺序分章到草稿区。创作子 agent 仅在作者要求时改正文；导入稿也要补当前版本独立评审，再逐章登记。抽取的人物与时间记录标明原文支持和待核实项。导入历史不足时明确缺口，不能把原稿直接装作已经完成全部检查。

导出只合并状态登记的正式章节，按 `number` 排序，校验正文哈希，目标必须在作品目录外，不能覆盖作品文件或混入资料和旧稿。导出前运行两个 `check`，检查 pending、文件与评审状态；不能将尚未同步的章节作为“完整定稿”交付。`novelctl export` 自身阻止未完成操作与正文哈希不符，评审语义和宿主身份不由导出命令认证。当前脚本仅 TXT/Markdown，DOCX 不是首版依赖。

普通导出标明为当前工作稿。以全书定稿交付时，先停止该作品写入，核验整体评审、作者约定并运行 `bookctl check`，随后导出同一版本；检查与导出之间正文或报告变化就重新核查。导出命令本身不会创建定稿记录，也不会把工作稿自动升级为文学定稿。

## 8. 换工具接续

整本复制作品文件夹，包括普通 JSON 和历史记录。新工具加载同一 Skill，从索引进入交接，读取当前方案、稿件哈希、授权、语言标准和已知风险，检查未完操作；再派新子 agent。

接续说明保持简短入口：最后完成章与故事时点、当前人物成长/关系阶段、活动故事线、关键事件、线索/知情/资源查询入口、最近评审与反馈、未核实项、下一步任务及必读文件。不要塞一份与原资料竞争的全书副本。

协议版本不认识时先保留文件，派资料子 agent 提出兼容方案；不能自动重建或覆盖整个目录。换平台不依赖旧子 agent 继续存活，依赖的是可读产物、身份来源与完整未完项。
